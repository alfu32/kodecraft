# L08 — Dependency invalidation and incremental generations

Status: done. Source baseline: `7d3e5953ec2de75f2b5e9c44fb3e65549d39ec68`.
Summary: `feat(intelligence): invalidate dependent files by semantic surface`.

`index/dependencies.rs` indexes incoming/outgoing file edges and computes a visited
closure, including seeds, through dependency cycles. `index/invalidation.rs`
separates content changes, public-surface changes and removals. Body-only edits
resolve the edited file. Changed/removed exports invalidate transitive dependents;
matching raw references/types/hints/imports wake files lacking an old dependency.
Matching includes previously resolved references so a newly introduced duplicate
definition cannot leave an old arbitrary binding intact. This matching is
conservative, as in the source planner; unrelated files with matching names may
also refresh. No filesystem scanning or reparsing occurs here.

`IncrementalSemanticIndex::prepare` merges extraction deltas, resets affected
enriched facts, and retains untouched symbol/occurrence/type/relation/expression
facts. Resolver passes process only affected files; global declaration indexes and
dependency edges are reconstructed from in-memory facts. Unchanged extraction
Arcs remain shared. Removed identities and their type shapes cannot survive query
validation. Rename is an atomic removal plus insertion under the new path-derived
identity. Conflicting duplicate updates and update/remove overlap are errors.

Semantic generations advance once per affected surviving file, independently of
document versions. Exact no-ops and metadata-only revision changes preserve the
generation. Overflow and cancellation return an error without changing the old
project. `SemanticCacheKey` includes file, content hash, parser/document version and
resolution generation. The affected/removed-file plan is the notification payload
for L09 token/completion consumers, delivered only after L05 persistence succeeds.
Preparation never publishes. L05's SQLite worker remains the publication owner;
no terminal or interactive-state mutation happens in this worker API.

Nine `tests/invalidation.rs` tests cover all five original SemanticInvalidationTest
scenarios and the implementation-only H2 persistence case through actual native
SQLite. They additionally cover physical rename, removal, ambiguous new exports,
transitive wake-up, unchanged document versions, exact no-ops, metadata-only edits,
cancelled/conflicting/exhausted updates, immutable old readers and C moved/changed
fields through typedef/pointer receivers. Incremental answers are compared with a
fresh full resolution: symbols, occurrences, relations, expression types and edges.
The restart test checks only Customer changes its stored bundle for a literal
edit, retains Service relations/generation/inferred type, then invalidates Service
correctly after reloading and changing the export.
