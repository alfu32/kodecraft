# R05 — SSE and WebSocket execution

Status: done

Source baseline: `7d3e5953ec2de75f2b5e9c44fb3e65549d39ec68`, clean.
Read both streaming methods of `RestHttp.kt`, all original `RestHttpTest` cases
and searched every REST/Main source path for WebSocket send calls. R04 is qualified.

Audit findings guiding implementation:

- Source SSE publishes newline-normalized lines, with a capped capture, but its
  `receivedBytes` is the retained count rather than the real received count.
  Native streaming must retain raw bytes separately, parse event boundaries and
  count all received chunks, preserving partial outcomes on cancellation/errors.
- Source WebSocket only receives: there is no `sendText`, `sendBinary` or other
  initial-payload send anywhere in the REST/Main implementation. Its incoming text/
  binary callback fragments are concatenated into the capped response and displayed
  with a newline at the end of a message. The task card now records that executable
  baseline; any optional explicit initial message is an extension.
- Source WebSocket reports every normal onClose as success without preserving its
  close code/reason. Native code must preserve the close information and distinguish
  abnormal closures. No reconnect/replay is authorized by baseline behavior.
- Selected actual APIs/source inspected: eventsource-stream 0.2.3,
  tokio-tungstenite 0.30.0, rustls-platform-verifier 0.7.1 and R04's already locked
  tokio-rustls 0.26.6/rustls 0.23.46. SSE parser strings/events and WebSocket messages
  require independent input bounds, not just a final preview cap. The selected SSE
  parser's initial BOM slicing uses a byte index of one; the adapter must strip a
  split UTF-8 BOM before parser input to avoid that panic while retaining raw bytes.

Implemented `kode-rest/src/stream/{mod,sse,websocket}.rs`, shared R04 metadata/
client helpers, loopback HTTP/SSE/WS/WSS fixtures and 13 focused checks (one unit
case plus 12 integration cases). All four source `RestHttpTest` cases now have
native translations across R04/R05.

- `stream::Executor` is an inert per-workspace owner around R04's HTTP executor
  and cookie jar. It consumes the same captured request/key/cancellation token and
  provides one bounded progress channel for all protocols. Ordinary HTTP retains
  source completion-only publication; SSE and WebSocket publish while running.
  The returned immutable `Response` is authoritative completion, independent of
  which request currently owns editor focus. An already closed owner channel
  prevents connection. A blocked send or read remains independently cancellable.
- Progress events carry the original execution key: opened headers/status/final
  URL plus normalized initial request/notices; retained byte chunks; parsed SSE
  events; counts/truncation; and WebSocket close details. Channel capacity is at
  most 64. Raw data events carry at most 16 KiB; UI owners append their bytes,
  replace progress counters and cap any formatted/event-history representation.
  The caller schedules/joins the future; no detached reader task mutates UI state.
- SSE reuses reqwest request settings, body, auth, cookies, redirects and TLS.
  `sse://` and Accept selection are exercised through the real resolver. Raw
  received bytes are retained separately from parsed event/data/id/retry fields.
  Multiline data, CRLF, inherited event IDs, UTF-8 splits and initial BOM work.
  Invalid UTF-8 is rejected promptly before the selected parser can accumulate
  an invalid prefix; the adapter retains at most three incomplete UTF-8 bytes.
  Non-SSE/non-200 diagnostic HTTP bodies remain inspectable responses.
- SSE parsing bounds are 64 KiB per line, 256 KiB per unfinished event/parsed
  event and 1 MiB per incoming chunk. Typed event display has an independent
  preview-sized byte budget and 4,096-record cap, with an explicit notice when
  reached. Raw preview/counters keep working after that display cap. The response
  prefix uses the configured R04 limit, while received counts include all chunks.
- WebSocket uses tokio-tungstenite's frame/UTF-8/message validation, with 64 KiB
  frame and 256 KiB complete-message limits, 16 KiB read/write buffers and a
  512 KiB maximum write buffer. Valid fragmented messages are assembled before
  publication and emitted as bounded chunks with a message-end flag. Binary bytes
  are unchanged; control frames do not become body bytes, and automatic pong/close
  acknowledgements are flushed. Unterminated/oversized messages fail explicitly.
  Received counts measure complete accepted message payloads, not TCP bytes or
  payload from a rejected incomplete frame/message. Callback fragment timing is
  not treated as a wire-frame contract.
- Close code/reason is retained; normal/away/empty closes succeed and abnormal
  codes or a dropped connection report failure with earlier data intact. A normal
  101 WebSocket result is successful in the native response helper. SSE and WS
  timeout applies to connection/handshake; established streams can remain open
  until EOF, peer close or explicit cancellation. No reconnect/replay occurs.
- WebSocket authentication, cookies, redirects and TLS are configured separately
  from reqwest. Header duplicates/normalization, HTTP-only/secure cookie origin
  mapping and Set-Cookie capture are qualified. Redirect enablement and the ten-hop
  limit are explicit; cross-origin auth/Cookie headers are stripped and downgrade
  is refused. Connections are direct. WSS uses the platform verifier and the same
  pinned rustls stack; explicit per-request bypass skips certificate/hostname
  validation while retaining cryptographic handshake-signature verification.
  A later validated request still rejects the self-signed fixture. URL userinfo
  is rejected with an instruction to use the supported request-auth fields.
- Default WebSocket execution sends no initial body, matching the audited source.
  `execute_with_initial(..., InitialMessage::Text|Binary)` is a clearly explicit
  extension, bounded to 256 KiB and validating text before connection. Its message
  is sent once after successful upgrade, never as an HTTP handshake body. Method/
  body/transport-header normalization is visible in progress metadata.
