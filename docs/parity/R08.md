Implemented:

- Native `execute_with_progress` preserves the existing executor entry point and
  adds a bounded (64-event) metadata channel for ordered Started/Completed events.
  Validation errors appear without transport; cancelled backpressure returns the
  accumulated partial summary before any next item starts. Closed/oversized
  progress owners fail before preparation.
- Application RunState drains bounded progress, stream events and final responses,
  retaining per-request outcomes and validation failures. The current request is
  visible even while ordinary HTTP waits for its complete response.
- A real runner pane presents progress, outcomes, Stop/Run again/Close and result
  navigation. F7 opens/focuses run history. Folder/collection runs open their form
  while preserving sidebar focus, so pressing Run again still cancels. Result
  navigation resolves captured runtime keys after moves, and explicitly refuses
  removed requests rather than opening a replacement path.
- Validation failures suppress stale prior responses for that request. Later
  successful preparation clears the stale failure. Runner state/progress/history
  remains runtime-only; existing response divider/Pretty/environment preferences
  stay in owned project UI state.

Qualification:

- `rest_app` has 24 real application cases. Runner cases cover in-flight HTTP
  progress, scope moves, invalid variables before transport, original result
  identities, deleted-target refusal, actual Stop/Run again buttons, and busy
  workspace cancellation with draft restore and disposed runtime owners.
- HTTP/SSE/WS use real loopback transports. SSE and WebSocket application cases
  now also restore their project and export through the sidebar without replay,
  preserving the original scheme/model and creating fresh runtime owners.
- A 40-request application run keeps every outcome in order while retaining the
  bounded newest 32 response previews (192 MiB total conservative budget). Opening
  an evicted result shows an explicit retention message and never replays it.
  Deleted runtime keys also release cached validation failures.
- `rest_runner` covers keyboard/page following, independent wheel scrolling,
  scrolled row mouse targets, distinct Stop/Rerun/Close actions and tiny views.
- `test-rest-runner-terminal.py` runs four actual CLI PTYs at 100×34 and 60×34.
  It creates/renames a folder and two requests, edits variable-bearing URLs,
  sends each request, runs only that folder in order, opens both captured results,
  changes Pretty/divider preferences, exports, quits, restores the selected
  request and explicitly sends again. Export equals the persisted collection;
  unknown collection/variable fields survive. The new workspace cookie jar starts
  empty, while cookies carry between requests before restart. Runtime outcomes
  and response text are absent from persistence. No Java is present/required.
  [Recorded terminal evidence](R08-pty.json).
- R06's four management/environment PTYs and R07's four editor/response PTYs also
  pass on the runner-enabled binary. Terminal modes/termios restore in all cases.
