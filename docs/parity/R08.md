# R08 — Collection runner, persistence and REST qualification

Status: in-progress

Source baseline: `7d3e5953ec2de75f2b5e9c44fb3e65549d39ec68`, clean.
Prerequisites R07, W03 and W05 have complete implementation/acceptance reports.

Source references: `Main.kt:1639` collection/folder depth-first run selection,
`RestRunSummary`, `RestEditorView.kt` run history/summary/result navigation, and
all five source REST test suites. R06 supplied the real immutable sequential
executor; R07 supplied the actual request/response editors and complete buffer
ownership. Backend availability and completion counts alone do not complete R08.

Implemented in progress:

- Native `execute_with_progress` preserves the existing executor entry point and
  adds a bounded (64-event) metadata channel for ordered Started/Completed events.
  Validation errors appear without transport; cancelled backpressure returns the
  accumulated partial summary before any next item starts. Closed/oversized
  progress owners fail before preparation.
- Application RunState drains bounded progress, stream events and final responses,
  retaining per-request outcomes and validation failures. The current request is
  visible even while ordinary HTTP waits for its complete response.
- A real runner pane presents progress, outcomes, Stop/Run again/Close and result
  navigation. F7 opens/focuses run history. Folder/collection runs open their form
  while preserving sidebar focus, so pressing Run again still cancels. Result
  navigation resolves captured runtime keys after moves, and explicitly refuses
  removed requests rather than opening a replacement path.
- Validation failures suppress stale prior responses for that request. Later
  successful preparation clears the stale failure. Runner state/progress/history
  remains runtime-only; existing response divider/Pretty/environment preferences
  stay in owned project UI state.
